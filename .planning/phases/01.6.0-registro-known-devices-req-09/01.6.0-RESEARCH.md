## Summary

La fase 1.6.0 reemplaza el diálogo `SourcePickerDialog` (lista simple con botones) por un nuevo `AddSourceDialog` con tabla plana de 3 secciones (física, WiFi, FTP), sustituye el reorganizador `reorganize_by_metadata` por un flujo nuevo con carpeta `SinClasificar/` y verificación MD5, y corrige bugs de threading COM y timers. El árbol está limpio tras la limpieza post-incidente (commit `857d63d`), el fix SC4 (`_reset_mtp_thread_local` + `_reset_ingestors`) ya está commiteado, y `add_source_dialog.py` y `reorganize_dialog.py` no existen aún — se crean desde cero. La UI-REVIEW (`01.6.0-UI-REVIEW.md`) audita el `add_source_dialog.py` como si ya existiera (fue parte del intento revertido), pero los hallazgos son directrices de diseño válidas para la implementación nueva.

**Primary recommendation:** Crear `add_source_dialog.py` y `reorganize_dialog.py` como módulos nuevos, integrarlos en `main_window.py` reemplazando las llamadas a `SourcePickerDialog` y `_reorganize_by_metadata`, y eliminar `source_picker.py` y su test.

### Pattern 1: Diálogo Qt con tabla QTableWidget embebida
**What:** El `AddSourceDialog` usa un `QTableWidget` con `setCellWidget` para composiciones complejas por celda (checkbox + label + botón).
**When to use:** Cuando se necesita una tabla con widgets interactivos por celda, no solo texto.
**Example:**
```python
# Basado en el patrón de _build_path_widget (main_window.py:2417-2438)
class AddSourceDialog(QDialog):
    def _build_row(self, row, source):
        widget = QWidget()
        lay = QHBoxLayout(widget)
        lay.setContentsMargins(4, 0, 4, 0)
        cb = QCheckBox()
        cb.setChecked(source.get("enabled", True))
        lay.addWidget(cb)
        lbl = QLabel(source["path"])
        lay.addWidget(lbl, 1)
        # ... nombre editable, estado, papelera
        return widget
```

### Pattern 2: Worker QThread para operaciones off-thread (D-09, D-15)
**What:** Operaciones pesadas (WPD enumeration, camera detection) se ejecutan en QThread via `_TaskWorker` o `_StageWorker`.
**When to use:** Cuando la operación puede bloquear la UI (WPD COM de 2-5 segundos, detección de cámara).
**Example:**
```python
# Basado en _StageWorker/_TaskWorker (main_window.py:91-147)
class _CameraDetectWorker(QObject):
    progress = Signal(str)
    done = Signal(bool, object)
    
    def run(self):
        try:
            metadata = metadata_engine.get_video_metadata(self._file_path)
            self.done.emit(True, metadata.get("camera_model", ""))
        except Exception as e:
            self.done.emit(False, str(e))
```

### Pattern 3: CoInit/CoUninit balanceado (D-24)
**What:** En `WpdBackend.list_devices()` (mtp.py:446-477), actualmente se hace `CoInitialize()` al inicio y `CoUninitialize()` en finally. El problema es que si el hilo ya tiene COM inicializado (conteo de refs), la llamada adicional incrementa el conteo y la llamada lo decrementa, pero si el thread-local ya tenía un `DeviceManager` del `list_devices` anterior, el reemplazo de `_manager_local` (D-23) puede dejar referencias stale.
**When to use:** En toda operación COM que pueda ejecutarse en un hilo que ya tiene COM inicializado.
**Verificación actual (mtp.py:446-477):**
```python
def list_devices(self) -> List[DeviceInfo]:
    comtypes.CoInitialize()    # incrementa ref count
    try:
        DM = _manager()         # usa _manager_local (thread-local)
        # ... enumeración ...
    finally:
        comtypes.CoUninitialize()  # decrementa ref count
```
**Fix D-24:** Verificar si COM ya estaba inicializado en el hilo antes de CoInitialize, y solo hacer CoUninitialize si esta llamada hizo el CoInitialize (patrón reentrante). Usar `comtypes.co_initialized()` o un flag `threading.local()` para rastrear si el owner hizo el init.

### Anti-Patterns to Avoid
- **SenderEditDialog.exec() en tests offscreen:** Cuelga porque QDialog.exec() entra en un event loop Qt que no se resuelve en offscreen sin un eventos externo. El skip en test_source_picker.py:266 documenta esto. **Solución para el nuevo add_source_dialog:** para el flujo FTP/WiFi que pide nombre, no usar `.exec()` modal; usar patrón inline o confirmación por señal.
- **Llamar `sender_list.clear()` sin preservar selección:** La UI-REVIEW (hallazgo BLOCKER) documenta que `_populate_guardados()` destruye selecciones cruzadas. El nuevo diálogo debe guardar/restaurar selección o刷新ar solo la lista afectada.
- **Reiniciar `_manager_local` sin esperar staging thread:** El fix SC4 actual (L4094-4108) resetea el thread-local y el stage_thread, pero no usa `thread.wait()` para esperar la terminación real del hilo. Agregar `_stage_thread.wait(2000)` antes de resetear.

## Common Pitfalls

### Pitfall 1: SenderEditDialog.exec() cuelga en tests offscreen
**What goes wrong:** `SenderEditDialog` (wifi_panel.py:45) es un `QDialog` que al hacer `.exec()` entra en un event loop modal. En tests Qt offscreen, si no se simula el OK/Cancel, el test cuelga indefinidamente.
**Why it happens:** Qt offscreen no procesa eventos externos de la misma forma que un display real; `exec()` espera que el usuario cierre el diálogo.
**How to avoid:** En el nuevo `AddSourceDialog`, el flujo FTP que pide nombre (D-04) NO debe usar `SenderEditDialog.exec()`. Alternativas: (a) un `QLineEdit` inline en la fila de la tabla FTP, (b) un non-blocking popup con señal de confirmación, o (c) mockear el `SenderEditDialog` en tests como se hace con `FakeDeviceDialog` en test_source_picker.py.
**Warning signs:** Test que no avanza; timeout en unittest.

### Pitfall 2: WiFi desaparece al abrir QR (D-07)
**What goes wrong:** Al abrir el QR de un origen WiFi, el `_refresh_source_list` se ejecuta y recrea la tabla, perdiendo la referencia al origen WiFi.
**Why it happens:** `_show_wifi_qr_for_sender()` probablemente provoca un refresh de la tabla que recrea las filas sin preservar el estado.
**How to avoid:** Asegurar que `_show_wifi_qr_for_sender()` NO provoke `_refresh_source_list()` o que el refresh mantenga los orígenes existentes. El QR se muestra en un panel flotante separado (`ShootInboxPanel`) que no debería afectar la tabla.

### Pitfall 3: Unknown_Camera hardcodeado en 27 sitios
**What goes wrong:** El string `"Unknown_Camera"` aparece en 27 archivos/líneas. Si se reemplaza por `"SinClasificar"` (D-16) sin actualizar todos los puntos, se crean inconsistencias.
**Why it happens:** El nombre de carpeta fallback está inline en múltiples módulos (ingestor, metadata_engine, selective_dump, tests).
**How to avoid:** Definir la constante `FALLBACK_CAMERA_NAME = "SinClasificar"` en un módulo central (p.ej. `ingestor.py` o `db.py`) y referenciarla en todos los puntos. Los 27 puntos de uso son:
- `ingestor.py`: L562, L565, L568, L571, L728, L731, L744, L752 (8 puntos)
- `metadata_engine.py`: L291, L335 (2 puntos)
- `selective_dump.py`: L47, L885, L886 (3 puntos)
- `main_window.py`: L628, L4710 (2 puntos)
- Tests: test_metadata_engine.py L225, L227; test_main_window.py L159; test_ingestor.py L106; test_wifi_source.py L817; test_e2e.py L119, L150, L158, L201, L213 (10 puntos)
- `tools/translate_en.py`: L69, L297 (2 puntos)

### Pitfall 4: `stop_ingest()` no espera staging thread
**What goes wrong:** `stop_ingest()` (L1781) detiene watchers e ingestors pero no espera `_stage_thread`, que puede estar ejecutando COM en otro hilo. Si se cambia de proyecto inmediatamente, el staging thread queda con referencias a un proyecto eliminado.
**Why it happens:** `stop_ingest()` solo llama a `ing.stop()` y limpia listas, sin gestionar el `_stage_thread`.
**How to avoid:** Añadir espera de `_stage_thread.wait(2000)` en `stop_ingest()` antes de permitir cambio de proyecto, o integrarlo en `_reset_mtp_thread_local()`.

### Pitfall 5: CoInit/CoUninit desbalanceado en `list_devices` (D-24)
**What goes wrong:** `WpdBackend.list_devices()` (mtp.py:446) hace `CoInitialize()` siempre, pero si el hilo ya tiene COM activo, esto incrementa el ref count sin que el `CoUninitialize()` posterior lo deshaga correctamente si ya había un Manager en `_manager_local`.
**Why it happens:** COM usa conteo de referencias; cada `CoInitialize()` incrementa y cada `CoUninitialize()` decrementa. Si el conteo llega a 0, COM se desinicializa para el hilo.
**How to avoid:** Verificar antes si COM ya está activo (flag en `threading.local()`) y solo hacer init/uninit si esta llamada fue la responsable.

### Pitfall 6: El fix SC4 ya commiteado no espera staging con `wait()`
**What goes wrong:** `_reset_mtp_thread_local()` (L4094) hace `_stage_thread.quit()` pero no `_stage_thread.wait(2000)`, como sí hace `prepare_for_update()` (L1812). Si el hilo tarda en terminar, el reset de `_manager_local` puede ejecutarse mientras el hilo todavía tiene referencias COM.
**Why it happens:** Diferencia entre `_reset_mtp_thread_local` y `prepare_for_update` en el nivel de limpieza.
**How to avoid:** Añadir `self._stage_thread.wait(2000)` después de `self._stage_thread.quit()` en `_reset_mtp_thread_local()`.

1. **¿Cómo se muestra "detectando..." en la tabla del AddSourceDialog mientras la detección de cámara está en curso?**
   - Qué se sabe: D-09 dice "popup non-blocking + fallback manual"; el nombre detectado se rellena editable y pendiente de confirmación.
   - Qué no está claro: si el popup es un QMessageBox no-bloqueante, un tooltip, o un widget inline en la fila de la tabla.
   - Recomendación: usar un `QLabel` inline con texto "Detectando..." en la columna nombre, reemplazado por el nombre detectado o "Sin nombre" al completar. Más discreto que un popup y consistente con la regla "no esconder nada".

2. **¿Cuántos archivos se espera en `SinClasificar/` típicamente?**
   - Qué se sabe: el reorganizador debe manejar de 1 a miles de archivos (un volcado completo de tarjeta SD).

   - Recomendación: ejecutar el escaneo en un QThread si >10 archivos, mostrar barra de progreso indeterminada.

3. **¿El "borrar dispositivos guardados" (D-11) afecta también a `sd_cards` o solo a `device_settings` y sesiones?**

   - Qué no está claro: si el kill-switch debe limpiar `sd_cards` también.
